# Discovery location, optional expansion, prompts and matched gallery

Apply the additive `DiscoveryLocationAndPrompts` migration before deploying the accompanying frontend. Existing prompts/location labels initialize empty, automatic location and expansion initialize false, ages initialize 18–99 with `DiscoveryAgeConfigured=false`. Existing coordinates/home city and profile data remain intact. The age-configured flag allows the app to retain old account-scoped local ages until an authoritative server age choice has been saved. No new server secret/provider key is required.

`GET/PATCH /me/discovery-settings` uses JWT ownership, the shared account lifecycle lock and a user row lock. Radius, interested-in, ages and expansion toggles update atomically. Location requires a valid coordinate pair and explicit automatic-location mode. Only the latest coordinates and a private city/country label/time are retained; no location history is added. Disabling automatic updates keeps the last saved discovery centre. Home city is not overwritten. Location coordinates remain owner-only; matched/discovery DTOs omit them. A movement flag is true on the first fix or at least 1 km movement, avoiding feed resets for small fluctuations. Account closure removes the profile/location fields through the existing erasure flow.

The app requests when-in-use permission from a settings action. Foreground refresh runs on entry/resume and a throttled foreground timer, with stale/background/account-switch writes rejected by the client. Native Android/iOS GPS/permission/geocoder behavior still needs real-device verification; an API/container check cannot certify those sensors.

Expansion is opt-in. A bounded SQL candidate query uses a latitude range and dateline-aware longitude range, an IsVisible/Lat index and approximate proximity ordering before exact distance filtering. At most 1,000 candidates are materialized. Strict results always win; fallback is used only when strict results are empty. Distance fallback is max(radius + 25 km, radius × 1.5), capped at 450 km; age fallback is ±5 years, bounded 18–100. Neither relaxes gender, block, pause/closed, incognito visibility or already-swiped exclusions. The returned DTO marks outside-age/distance results. Larger production datasets still require actual query/device performance monitoring; this is a bounded candidate strategy, not a global spatial index.

`GET /profiles/{other}` requires an existing match, rejects either-direction blocks and closed targets, and returns the shared public profile presentation including all photos/bio/prompt. It exposes no exact coordinates or private discovery-place label. Unmatch/block guards remain effective for clients already viewing a profile.

`PromptKey`/`PromptAnswer` are optional paired public profile fields (60/250 UTF-16-unit maximum; five supported question keys). Public writes validate the pair; private resumable drafts may retain incomplete work. Clearing both deletes the public prompt. Bio remains a separate 1,000-unit field. Profile completion/account closure keep their existing draft cleanup and erasure behavior. Inactive private draft text still needs the previously documented launch retention policy.

Validation includes relational HTTP tests for gallery ownership, reverse block/closure/unmatch, coordinate privacy, atomic invalid settings, prompt persistence/clearing, opt-in fallback/strict priority, travel, date-line/polar distance queries and small GPS changes. Real PostgreSQL checks upgrade/rollback/reapply from the old schema, validate location/fallback SQL and matched DTOs, then run the existing concurrency/photo/account/load scenarios. Test data is disposable; no real users or provider assets are used.

After merge, deploy the backend latest commit/migration first, then update the frontend. Do not roll back columns holding real new location/prompt/preferences data without a data-preservation plan. Live Cloudinary behavior, real phone UI/GPS, payments, store signing and measured production performance remain separate release checks.
